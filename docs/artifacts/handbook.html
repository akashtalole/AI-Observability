Enterprise AI Observability Handbook

Guidance, architecture, design patterns and tooling choices for observing enterprise AI applications — RAG systems, agents, chatbots, copilots and more.

The north-star goal

Full visibility into latency, quality and cost of every AI application, across any time range (last 5 minutes to last 18 months), so issues are caught early and trends are tracked over months.

Why AI observability

Traditional monitoring answers "is the service up and fast?". For AI applications that is necessary but not sufficient: a RAG app can return HTTP 200 in 800 ms with a confidently wrong, ungrounded or unsafe answer, at ten times the expected cost.

The three pillars for AI: latency, quality, cost

flowchart LR
    A[AI request] --> L[Latency<br/>TTFT, total, per-stage]
    A --> Q[Quality<br/>groundedness, relevance,<br/>task success, safety]
    A --> C[Cost<br/>tokens, tool calls,<br/>retrieval, infra]
    L --> T[Trade-off decisions<br/>model, prompt, k, cache]
    Q --> T
    C --> T

These three are coupled. A cheaper model lowers cost but may reduce quality; a larger top_k may raise quality but increases latency and cost. Observability exists to make those trade-offs measurable and reversible.

Failure modes that only AI observability catches

Failure Looks like in APM What you need
Silent quality regression after a prompt/model/index change Nothing Online evals + release annotations
Retrieval drift (stale/poisoned index, embedding model change) Nothing Retrieval relevance, context precision/recall, index freshness
Cost explosion (agent loop, long context, retry storm) Slightly higher latency Token/cost per trace, per tenant, per feature
Provider-side model update ("silent" version drift) Nothing Pin model versions; track response fingerprint & eval baselines
Hallucination / ungrounded answers 200 OK Groundedness / citation-support score
Prompt injection, data leakage, jailbreak Nothing Guardrail verdicts, PII detections, red-team canaries
Agent loops, wrong tool selection Long latency Step counts, tool-call success, trajectory evals
Rate limiting / quota exhaustion 429s Per-model quota headroom, fallback rates

Outcomes you should be able to claim

  1. Detect a latency, quality or cost regression within minutes (alerts) or days (trend/drift).
  2. Explain any single bad answer end-to-end (trace → retrieved chunks → prompt → model → answer → evaluator score).
  3. Attribute cost to tenant, feature, model, prompt version and team (FinOps/showback).
  4. Prove to risk/compliance what the system did (audit, lineage) without over-collecting personal data.
  5. Trend all of the above over months, annotated with every change (model, prompt, index, config, code).

How AI observability differs from traditional APM

Dimension Traditional services AI applications
Behavior Deterministic; same input → same output Non-deterministic; temperature, retrieval and model drift
Correctness signal Status code, assertions Needs evaluation (heuristic, model-as-judge, human)
Latency shape Roughly normal; p99 meaningful Long-tailed, depends on output length; need TTFT and tokens/sec
Cost model Mostly infra (CPU/memory), flat-ish Per-token and per-call variable cost on every request
Payloads Small, structured, mostly safe to log Large free-text prompts/responses; contain PII and secrets
Dependencies Services, DBs Model providers, vector DBs, rerankers, tools, MCP servers, other agents
Failure Errors, timeouts Plausible-but-wrong, refusals, loops, unsafe output
Change surface Code deploys Code + prompt + model version + index + embedding + config + tools
Debugging unit Trace of service calls Trace + retrieved context + prompt + tool I/O + judge scores
Retention need Days–weeks of detail Weeks of detail, months–years of aggregates (trend, regression, audit)

What stays the same

Do not build a separate silo. AI telemetry should ride on your existing observability stack where possible: same trace context propagation (W3C traceparent), same SLO and on-call practice, same identity and access model. The AI-specific layer adds semantics (prompts, tokens, evals) not a parallel universe.

Rule of thumb

Reuse APM for infrastructure, golden signals and distributed tracing. Add an LLM-aware layer for content, evaluation, cost attribution and prompt/dataset management. Whether that layer is one product or two is the build-vs-buy question.

OpenTelemetry GenAI semantic conventions

OpenTelemetry defines gen_ai.* attributes, spans and metrics for model calls, agents and tool execution. Status: Development (not stable) as of mid-2026 — attribute and metric names may change between versions. Pin the semconv version you target and use OTEL_SEMCONV_STABILITY_OPT_IN as the conventions describe.

Commonly used attributes (verify against the version you target):

Attribute Meaning
gen_ai.operation.name chat, embeddings, execute_tool, invoke_agent, …
gen_ai.provider.name (older: gen_ai.system) Provider, e.g. openai, anthropic, aws.bedrock
gen_ai.request.model / gen_ai.response.model Requested vs actually served model
gen_ai.request.temperature, .max_tokens, .top_p Request parameters
gen_ai.usage.input_tokens / gen_ai.usage.output_tokens Token usage

Metrics: client operation duration, client token usage (histograms), plus server-side time-to-first-token / time-per-output-token for model servers.

Message content (prompts/completions) is opt-in by design — treat it as sensitive and capture it through a controlled path (see Security & privacy).

Portability principle

Instrument with OpenTelemetry (or an OTel-compatible library), add your own app.* attributes for business context, and send through an OpenTelemetry Collector you control. Backends then become swappable without re-instrumenting.

Key design decisions

  1. Gateway or no gateway? A gateway gives uniform metering and policy for all model traffic; it is the easiest place to get cost and rate-limit visibility. Instrumenting in-app gives richer semantic context (retrieval, prompt versions). Most enterprises do both: gateway for metering/policy, app SDK for semantics, joined by traceparent.
  2. Evaluation off the hot path. Never block the user request on an LLM judge. Emit trace → evaluate asynchronously → write scores back keyed by trace_id.
  3. Two stores, two jobs. Traces optimize for debugging a single request (short retention, high detail). A wide per-request fact table optimizes for trend analysis (long retention, columnar, cheap aggregates). Do not try to serve month-over-month analytics from a trace backend.
  4. Rollups for long ranges. Dashboards over 6–18 months must read pre-aggregated data (see Storage & retention).
  5. Release annotations. Every deploy, prompt version, model change, index rebuild writes an annotation/event so a trend shift can be tied to a cause.

Design patterns for AI observability

Instrumentation patterns

1. Gateway metering

Route all model calls through an AI gateway that stamps tenant, feature, model, tokens, cost on every call. Gives complete cost coverage even for un-instrumented apps. Trade-off: extra hop (~ms) and a shared failure domain — deploy redundantly.

2. OTel-first, vendor-second

Instrument with OpenTelemetry; export to a Collector; fan out to one or more backends. Benefit: swap vendors without touching app code.

3. Semantic wrapper (decorator) layer

Wrap retrieve(), rerank(), generate(), call_tool() in your own thin library that emits spans with the app.*/rag.* namespace. One library, used by every team, enforces consistent attributes and redaction.

4. Trace-linked evaluation (score write-back)

Evaluators consume sampled traces and write scores back to the same trace_id. Dashboards then slice quality by any trace attribute (tenant, prompt version, index version).

5. Shadow / canary evaluation

Send a copy of a sample of traffic to a candidate model/prompt/index; compare scores, latency and cost against production before promotion. Pair with feature flags and automatic rollback on SLO breach.

6. Golden-set regression gate

Curated Q&A set with expected facts/sources runs in CI and nightly in production-like config. A drop beyond threshold blocks release and pages the owner.

7. Feedback loop (data flywheel)

User thumbs/edits, escalations, and low-score traces are queued for review, triaged, then promoted into the golden set. Closes the loop between production and offline evaluation.

Data patterns

8. Wide event per request

Persist one denormalized row per request/turn (50–150 columns) with latency per stage, tokens, cost, config versions, eval scores and user outcome. Cheap to aggregate for any time range; the backbone of trend analysis. See Storage.

9. Tiered retention

Full detail short, aggregates long, raw content only where policy allows. See Storage.

10. Content by reference

Store prompt/response bodies in a governed, access-controlled store; keep only IDs, hashes, lengths and redacted snippets in the general telemetry path.

11. Change events as first-class data

Deploys, prompt versions, model switches, index rebuilds, embedding changes, feature-flag flips, provider incidents — all written as events so dashboards overlay them on every chart.

Reliability patterns

12. Telemetry must not break the app

Async batching, bounded queues, drop-on-overflow, timeouts; never block the request on export. Measure telemetry loss itself (dropped spans).

13. Budget guardrails

Per-tenant/feature token and cost budgets enforced at the gateway, with burn-rate alerts (e.g. 2% budget in 1 hour) and circuit breakers for runaway agents (max steps, max tokens, max wall-clock).

14. Provider fallback with attribution

Fallback chains (primary → secondary model) must record which model served the response; otherwise quality and cost shifts are invisible.

Anti-patterns

Anti-pattern Why it hurts
Logging full prompts everywhere "just in case" PII/secret exposure, huge storage bills, compliance risk
Judging 100% of traffic with a frontier model Evaluation cost rivals product cost; sample and tier judges
Only averages Long-tailed latency and cost hide in p95/p99 and top-1% tenants
No version tags Cannot attribute a regression to a prompt/model/index change
Treating thumbs-up as ground truth Sparse and biased; combine with automated and human evals
Separate silo per team Inconsistent attributes make enterprise rollups impossible
Alert on every score dip Alert fatigue; alert on SLO burn and statistically significant shifts

Why a wide fact table

One row per request/turn means any question — "p95 retrieval latency by index version for tenant X in March" — is a single GROUP BY. Metrics TSDBs cannot answer high-cardinality questions (tenant × prompt × model) cheaply; traces cannot do cheap aggregates over months.

See the schema in examples/sql/clickhouse_schema.sql and queries in Dashboards & queries.

Rollups and percentiles

  • Store histogram/quantile states (quantilesTDigest, quantileState, or Prometheus native/classic histograms) in rollups. Never average percentiles — merge their states.
  • Keep three granularities: 1-minute (alerting, ≤30 d), 1-hour (weeks–months), 1-day (quarters–years).
  • Roll up by dimension sets you actually need: {app, env}, {app, tenant}, {app, model}, {app, prompt_version}, {app, index_version}.
  • Cardinality guardrails: never put user_id, trace_id, or raw query text on metric labels. Tenant is acceptable only with a bounded tenant list (use top-N + "other").

Sampling strategy

Traffic Strategy
Errors, guardrail hits, slow (> p95), low eval score, thumbs-down Keep 100% (tail-based sampling)
High-value tenants / regulated flows Keep 100% of metadata; sample content
Healthy bulk traffic 1–10% for full traces; 100% for the wide fact row and metrics
Online evaluation Stratified sample (per tenant/feature/intent), e.g. 2–5% + all flagged traces

Always compute metrics from unsampled data (Collector spanmetrics/signaltometrics before the sampler, or app-side metrics) so rollups are not biased.

Sizing back-of-envelope

requests/day   × avg spans/request × ~1 KB/span   = hot-tier bytes/day
requests/day   × ~1–2 KB wide row (compressed 5–10x) = warm-tier bytes/day
content bytes  = requests × (prompt+context+answer chars) — dominant; gate with policy

Example: 5 M requests/day × 15 spans × 1 KB = 75 GB/day raw traces (before compression and sampling) — which is why full-trace retention is days, not months, while the wide row (≈10 GB/day raw, ≈1–2 GB compressed) comfortably covers 18 months.

Time-range UX requirements

  • Dashboards pick the rollup granularity from the selected range (≤6 h → 1-min; ≤14 d → 1-hr/5-min; >14 d → 1-hr/1-day).
  • Always show release/prompt/model/index annotations on the time axis.
  • Provide period-over-period (week-over-week, month-over-month) and baseline bands (rolling 28-day median ± MAD).
  • Retain eval scores at the same granularity as latency so quality and latency can be viewed together.

Security, privacy & governance

AI telemetry contains the most sensitive data your company produces at scale: employee and customer questions, internal documents (via retrieval), and model outputs. Treat the observability platform as a regulated data system.

Threats and controls

Risk Control
PII/PHI/PCI/secrets in prompts and responses Redact at the edge (SDK or Collector transform/redaction processors, or Presidio-style detectors) before export; deny-list for known secret formats
Over-collection of content Default to metadata only; content capture is opt-in per app, per tenant, per environment, time-boxed
Unauthorized access to traces RBAC/ABAC mapped to tenant and data classification; audit access logs; break-glass workflow
Cross-tenant leakage in shared dashboards Tenant-scoped views / row-level security; separate projects per business unit if needed
Vendor data residency & training use Region pinning, DPA, "no training on customer data", BYOK; prefer self-hosting or Collector-redacted SaaS for regulated data
Retention beyond policy / right-to-erasure TTLs per tier; deletion by subject_id pseudonym; content-by-reference makes erasure tractable
Prompt injection via retrieved docs, observed in traces Track injection detections; treat trace content as untrusted when rendering (escape HTML/markdown, never auto-execute)
Telemetry as exfiltration path Egress allow-lists for exporters; private endpoints

Data classification for AI telemetry

Class Examples Default handling
Operational metadata Latency, token counts, model, status, versions Broad access, long retention
Business context Tenant, feature, intent label, cost Role-based access, long retention
Derived scores Eval scores, guardrail verdicts Broad access, long retention
Content (redacted) Truncated/redacted prompt & answer Restricted, short retention
Content (raw) Full prompts, retrieved chunks Highly restricted, minimal retention, encrypted, audited

Governance and compliance mapping

  • Model & app inventory: every AI app registered with owner, risk tier, model(s), data sources — feeds dashboards and audits.
  • Regulatory alignment: EU AI Act (logging/traceability for high-risk systems, post-market monitoring), NIST AI RMF (Measure/Manage functions), ISO/IEC 42001 (AI management system), SOC 2 / HIPAA / GDPR for data handling. Observability evidence (eval results, incident records, change history) is the raw material for these.
  • Audit trail: immutable record of who changed which prompt/model/index/guardrail and when, linked to subsequent metric shifts.
  • Human oversight: review queues for flagged traces with documented outcomes.

Safety observability (what to detect and log)

  • Guardrail verdicts per category (toxicity, PII, jailbreak, prompt injection, off-topic, policy) with action taken (block/redact/warn).
  • Refusal rate and over-refusal (false positive) rate — both are quality signals.
  • Groundedness failures on regulated content (medical, legal, financial).
  • Red-team canary prompts run continuously against production config.
  • Tool-use authorization decisions for agents (what was allowed/denied and why).

Minimum viable control set

  1. Metadata-only by default; content capture behind a flag.
  2. Redaction in the Collector, tested with seeded PII fixtures in CI.
  3. Tenant-aware RBAC and audit logging on the observability UI.
  4. Retention TTLs enforced by storage policy, not by convention.
  5. Documented data-flow diagram reviewed by security/privacy.

Triggers to revisit the decision

  • Observability spend > 10–15 % of the AI platform spend.
  • Vendor acquired / relicensed / enters maintenance mode (this has happened repeatedly in the category).
  • Move to multi-cloud or sovereign-cloud requirement.
  • Span/event volume grows 5× (pricing cliffs).
  • New regulation requiring on-prem evidence retention.

Anti-patterns in the decision

  1. Building a trace UI from scratch — OSS options are mature; build only the differentiating layer.
  2. Buying a platform but skipping instrumentation standards — creates lock-in at the SDK level.
  3. Evaluating tools on demos, not on your traces — run a 2-week bake-off on real (redacted) traffic with a scorecard.
  4. Ignoring exit cost — require a data-export path and OTel compatibility in the contract.

Bake-off plan (2 weeks)

  1. Pick 2–3 candidates covering different archetypes (e.g. SaaS, OSS self-host, cloud-native).
  2. Instrument one real RAG flow through the same Collector, fan out to all candidates.
  3. Run the same 200-question golden set + a replay of 1 day of redacted traffic.
  4. Score: setup effort, trace fidelity, eval workflow, dashboards for latency/quality/cost, query flexibility (can you answer "p95 retrieval latency by index version last quarter"?), export, access control, cost projection.
  5. Decide; document in an ADR.

Cloud-agnostic approach

Goal: keep instrumentation, data and dashboards portable across AWS, Azure, GCP, on-prem and multiple model providers.

Principles

  1. OpenTelemetry end to end — SDK → Collector → any backend.
  2. Own the Collector — redaction, sampling and routing logic lives in your config, not in a vendor.
  3. Own the wide fact table — long-range truth sits in a store you control (ClickHouse, Iceberg/Parquet lakehouse, or your warehouse).
  4. Gateway abstraction — LiteLLM/Portkey/Envoy AI Gateway/TensorZero abstract providers and meter usage uniformly.
  5. Kubernetes-friendly — everything deployable via Helm/Terraform on any cloud.

Levers to cut observability cost (any option)

  1. Sample healthy traces, keep 100 % of errors/slow/low-score (tail sampling).
  2. Compute metrics before sampling; sample only the trace bodies.
  3. Content by reference, truncated content, shorter hot retention.
  4. Tier judges: heuristic checks on 100 %, small-model judge on sampled, frontier judge on flagged/golden sets.
  5. Drop low-value spans (internal chunk-loop spans) — aggregate into attributes instead.
  6. Compress and downsample warm data into rollups.

Decision hint

If observability + eval cost projects above ~10 % of LLM inference spend, or the vendor price curve is superlinear in your growth, evaluate self-hosting the high-volume path (traces, facts) while keeping SaaS for the high-value collaboration features (prompt management, annotation, eval UI).

Market dynamics to plan around

  • Consolidation. Observability platforms are being acquired by data, APM and AI-infrastructure companies (e.g. Langfuse by ClickHouse, announced January 2026; Helicone reported to have joined Mintlify in March 2026 and moved to maintenance mode). Insist on OTel ingest/export and data-export rights.
  • OpenTelemetry convergence. Nearly every vendor now ingests OTLP and GenAI semconv, shifting differentiation from collection to evaluation, analysis and workflow.
  • APMs moving up-stack. Datadog, Dynatrace, New Relic, Grafana, Splunk, Elastic ship LLM/agent modules; LLM-native vendors respond with broader infra and security features.
  • Agent observability (multi-step trajectories, tool calls, MCP) is the current frontier; assess trace UX for long, branching runs.
  • Evaluation cost is a first-class budget line; look for tiered/cheap evaluators and sampling controls.
  • Licensing drift. "Open source" ranges from MIT/Apache to source-available (Elastic License 2.0, FSL). Read the license for your intended use.

Evaluation criteria for any tool

  1. OTLP ingest and data export; GenAI semconv support level.
  2. Trace fidelity for RAG (retriever/reranker spans, chunk-level scores) and agents (nested steps, tool I/O, loops).
  3. Evaluation: built-in metrics, custom judges, online scoring on production traces, dataset/experiment workflow, CI integration.
  4. Cost: token → $ mapping with custom price tables, per-tenant/feature attribution, budgets.
  5. Time-range support: retention, rollups, SQL/API access for months-long trends.
  6. Security: SSO/SCIM, RBAC, audit logs, PII redaction, regions, self-host/BYOC.
  7. Scale and pricing model (per span/event/seat/GB) at 3× volume.
  8. Alerting and integrations (PagerDuty, Slack, Jira, CI).

Burn-rate formula

burn_rate = (observed bad-event ratio) / (1 - SLO target)
page when burn_rate(1h) > 14.4 AND burn_rate(5m) > 14.4     # ~2 % of 30-day budget in 1h
page when burn_rate(6h) > 6   AND burn_rate(30m) > 6
ticket when burn_rate(3d) > 1

Reducing noise

  • Alert on user-visible SLO impact first; route diagnostic signals to dashboards.
  • Require minimum sample size before quality alerts (e.g. ≥ 200 scored traces/window).
  • Group by app + change event to avoid duplicate pages.
  • Every alert links to: dashboard, example traces, last change events, runbook (runbooks).

Evaluation & quality measurement

Quality is the hardest of the three pillars because correctness is not directly observable. Build a layered evaluation strategy.

Evaluation layers

Making judges trustworthy

  1. Calibrate judges against 100–300 human-labelled examples; report agreement (Cohen's κ / Spearman).
  2. Pin judge model + prompt version; record in eval_version. Changing the judge breaks trend continuity — re-score a baseline slice when you do.
  3. Mitigate bias: position, verbosity, self-preference (use a different model family from the generator where possible).
  4. Use rubrics with decomposed claims (extract claims → verify each against context) rather than a single 1–10 score.
  5. Track judge cost and latency as first-class metrics.
  6. Run judge drift checks: re-score a fixed anchor set weekly.

Sampling for online evals

Stratify by app × tenant tier × intent; add 100 % of: thumbs-down, escalations, guardrail hits, low retrieval score, slow or costly outliers; plus a small always-on random slice for unbiased baselines.

  • Version everything: eval_version, judge prompt, rubric, model.
  • Keep an anchor set re-scored on every judge change.
  • Report confidence intervals; show sample size on charts.
  • Segment by intent/topic — aggregate means hide regressions in important slices.

RAG playbook: latency, quality & cost over any time range

Goal: full visibility into latency, quality and cost of the RAG app across any time range, catching issues early and tracking trends over months.

The recipe in seven steps

flowchart LR
    A[1 Instrument<br/>stage spans + versions] --> B[2 Meter<br/>tokens, cost, latency<br/>pre-sampling]
    B --> C[3 Store<br/>hot traces + wide facts + rollups]
    C --> D[4 Evaluate<br/>async, sampled, version-pinned]
    D --> E[5 Visualize<br/>range-aware dashboards + annotations]
    E --> F[6 Alert<br/>SLO burn, drift, cost]
    F --> G[7 Review<br/>weekly trend + monthly report]
    G --> A

1. Instrument every stage

Create spans for rag.request → rag.retrieve (embed, search, rerank) → chat <model> → guardrail. Attach app.*, rag.*, gen_ai.* attributes including prompt, model, index and embedding versions. Code: examples/rag-otel/instrument.py, guide: Instrumentation.

2. Meter cost and latency from 100 % of traffic

Compute metrics (counters, histograms) before trace sampling. Compute cost at request time from a versioned price table you own: cost = in_tokens × p_in + out_tokens × p_out (+ embed + rerank + retrieval infra).

3. Store for every time range

  • Hot (7–30 d): traces for debugging.
  • Warm (13–24 mo): wide per-request fact table (schema).
  • Rollups: hourly/daily with mergeable quantile states so a 12-month chart reads thousands, not billions, of rows.

4. Evaluate quality continuously

  • Deterministic checks on 100 %; small-model judge on a stratified sample; strong judge on flagged traces; humans on calibration sets (Evaluation).
  • Scores written back keyed by trace_id and stored with eval_version.

5. Visualize with time-range-aware dashboards

Panels that pick rollup granularity from the selected range, overlay change events and show sample sizes. Layout in Dashboards & queries.

6. Alert early

  • Minutes: error/TTFT burn-rate, cost spike, retrieval emptiness, agent/loop runaway.
  • Hours–days: quality regression vs 28-day baseline, drift, index staleness.
  • Every alert links to a trace sample, dashboard and runbook (Runbooks).

7. Review trends on a cadence

  • Weekly: SLO attainment, top regressions, cost anomalies, new failure clusters → backlog.
  • Monthly: month-over-month cost per resolved query, p95 latency, quality by intent, model/prompt/index change log vs metrics, budget forecast.
  • Quarterly: build-vs-buy re-check, evaluator calibration, retention/cost tuning.

Reading trends correctly

  1. Always compare same-slice, same-evaluator-version windows.
  2. Use rolling baselines (28-day median ± MAD) to tell drift from seasonality (weekday/weekend, month-end).
  3. Check traffic mix before blaming the system: Simpson's paradox is common when intent mix shifts.
  4. Show sample size / confidence intervals on every quality chart.
  5. Tie shifts to change events; if none exists, suspect provider-side model changes or data drift.

Instrumentation guide

Approaches

Approach Effort Fidelity Notes
Auto-instrumentation (OpenLLMetry, OpenInference, OpenLIT, vendor SDKs) Low Provider/framework calls Good start; misses business context
Manual spans with OTel API Medium High Needed for retrieval stages, versions, cost
Gateway metering Low Model calls only Complete coverage, no semantics
Framework callbacks (LangChain/LlamaIndex/…) Low Framework steps Often bridged to OTel

Recommended: auto-instrument model + vector DB clients, add a thin manual layer for stage spans and app.*/rag.* attributes, meter at the gateway.

Steps

  1. Pick conventions. gen_ai.* for model calls; your own app.*/rag.* for the rest (Telemetry model).
  2. Create a shared wrapper library (ai_telemetry) exposing context managers/decorators: retrieval_span, llm_span, tool_span, record_cost, record_feedback.
  3. Propagate context across services, queues and MCP/tool calls (traceparent; carry conversation_id as baggage or attribute).
  4. Stamp versions at startup from config/CI: release_id, prompt IDs/versions, model, embedding model, index version.
  5. Compute cost in the wrapper from a versioned price table (cached/reasoning tokens priced separately).
  6. Handle streaming: record TTFT at first chunk, close the span on stream end or client abort; record finish_reason.
  7. Capture feedback with the originating trace_id so thumbs/edits join to traces and scores.
  8. Gate content capture by flag + sampling + redaction.
  9. Test: unit-test the wrapper with an in-memory exporter; assert required attributes exist; seed PII fixtures to verify redaction.

Required attribute contract (enforce in CI)

root_span: [app.tenant.id, app.feature, app.environment, app.release.id, cost.usd.total]
retrieve:  [rag.index.version, rag.embedding.model, rag.retrieval.top_k, rag.retrieval.count, rag.retrieval.top1_score]
llm:       [gen_ai.request.model, gen_ai.response.model, gen_ai.usage.input_tokens, gen_ai.usage.output_tokens, app.prompt.id, app.prompt.version]
tool:      [gen_ai.tool.name, tool.status]

Python example (runnable)

See examples/rag-otel/instrument.py: stage spans, versions, token/cost metrics, TTFT histogram. Excerpt:

with tracer.start_as_current_span("rag.request") as root:
    root.set_attribute("app.tenant.id", cfg.tenant)
    chunks = retrieve(query, cfg)            # rag.retrieve span: top_k, count, top1_score, doc_ids
    result = generate(query, chunks, cfg)    # chat <model> span: tokens, finish_reason, TTFT
    usd = (result.in_tok * p_in + result.out_tok * p_out) / 1_000_000
    root.set_attribute("cost.usd.total", usd)
    cost.add(usd, dims); ttft.record(result.ttft_s, dims)

Collector & pipeline

The OpenTelemetry Collector is the control point for redaction, sampling, enrichment and routing. Keep its config in Git; roll out with canaries.

Reference config: examples/otel-collector.yaml.

Pipeline order matters

flowchart LR
    R[OTLP receiver] --> ML[memory_limiter]
    ML --> RS[resource enrich]
    RS --> SM[spanmetrics connector<br/>100% of spans]
    RS --> RD[redact attributes]
    RD --> TS[tail_sampling]
    TS --> B[batch]
    B --> X1[Traces backend]
    B --> X2[ClickHouse facts]
    SM --> PM[Prometheus remote write]
  1. Metrics before sampling so rates, percentiles and costs are unbiased.
  2. Redact before export (and before tail-sampling buffers if memory dumps are a concern).
  3. Tail-sample on error, latency, eval flags, tenant tier; probabilistic for the rest.
  4. Batch last; set memory limits; use persistent queues for durability where needed.

Deployment

Pattern Use
Agent (sidecar/daemonset) Local buffering, resource detection
Gateway (central deployment, ≥2 replicas) Tail sampling needs all spans of a trace on one instance → use load-balancing exporter keyed by trace_id
Two-tier (agent → gateway) Recommended for scale

  • Monitor the Collector itself: otelcol_receiver_refused_spans, otelcol_exporter_send_failed_spans, queue size, memory.
  • Alert on telemetry loss (drop rate) separately from product SLOs.
  • Version-control and test configs (otelcol validate), including redaction fixtures.
  • Keep per-tenant routing rules for data-residency (EU tenants → EU backend).

Runbooks

Each alert should link to one of these. First move for any incident: check the change-event overlay (what changed in the last 24 h?).

Latency regression

  1. Confirm: TTFT vs total? p95 vs p50? Which tenants/features?
  2. Stage breakdown: which stage's share grew (embed / retrieve / rerank / LLM / tools)?
  3. Check provider status and regional latency; compare against another model/region if fallbacks exist.
  4. Check context_tokens and output length: longer prompts and answers drive latency and cost.
  5. Check vector DB saturation, index size/refresh, rerank service.
  6. Mitigate: reduce top-k/context, enable caching, route to faster model, scale replicas, shed load for low-tier tenants.
  7. Roll back the last change if correlated.

Quality regression

  1. Verify sample size and evaluator version (judge changes break trends).
  2. Slice: which intent/tenant/index/prompt version? Compare to the 28-day baseline.
  3. Inspect 10–20 lowest-score traces; classify: retrieval miss, ungrounded generation, prompt issue, format issue, data staleness.
  4. Retrieval metrics: top-1 score, empty rate, doc freshness.
  5. Check for provider-side model update (response_model, fingerprint) or embedding/index change.
  6. Mitigate: roll back prompt/index/model; pin versions; adjust retrieval; add guardrail.
  7. Add failing traces to the golden set.

Cost spike

  1. Break down by tenant, feature, model, prompt version, token direction.
  2. Look for: retry storms, agent loops (steps/task), context bloat (context_tokens), model change, cache miss surge, abuse/bot traffic, eval-cost surge.
  3. Apply guardrails: per-tenant rate limit/budget, max steps, max tokens, route to cheaper model.
  4. Fix root cause; add a regression alert.

Provider errors and rate limits

  1. Check error_type split (429, 5xx, timeout, content-filter).
  2. Verify quota/TPM headroom; request increase; spread across deployments/regions.
  3. Ensure fallbacks work and are attributed (fallback_used, response_model).
  4. Tune retries (exponential backoff + jitter, retry budget) to avoid amplifying the incident.

Retrieval degradation

  1. Empty-retrieval or low-score rate up? Which index/tenant?
  2. Check ingestion pipeline (failed docs, lag), index version, embedding model parity between query and index.
  3. Validate ACL filters (are legitimate docs excluded?).
  4. Re-run retrieval golden set; compare recall@k with last good index.
  5. Roll back index alias; fix ingestion; reindex.

Safety / guardrail incident

  1. Contain: tighten guardrail, disable affected feature/tool, block abusive tenant/user.
  2. Collect evidence (traces, policy decisions) under access control.
  3. Assess exposure (PII, cross-tenant) with security/privacy; follow breach procedure.
  4. Fix; add test cases to red-team suite; post-incident review.

Telemetry pipeline failure

  1. Check Collector metrics: refused/dropped spans, exporter failures, queue saturation.
  2. Fail open for the app (never block requests); enable local buffering.
  3. Backfill from logs/object store if available; annotate the gap on dashboards.

Post-incident

Blameless review: timeline with change events, detection gap (could we have caught it earlier with a leading indicator?), new alert/dashboard/golden-set items, owner and due date.
