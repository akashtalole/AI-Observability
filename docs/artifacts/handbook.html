Enterprise AI Observability Handbook

Guidance, architecture, design patterns and tooling choices for observing enterprise AI applications — RAG systems, agents, chatbots, copilots and more.

The north-star goal

Full visibility into latency, quality and cost of every AI application, across any time range (last 5 minutes to last 18 months), so issues are caught early and trends are tracked over months.

Why AI observability

Two different things

This handbook is mainly about observability for AI (observing AI applications). Using AI to do observability is a separate topic: see AI for observability vs observability for AI.

Traditional monitoring answers "is the service up and fast?". For AI applications that is necessary but not sufficient: a RAG app can return HTTP 200 in 800 ms with a confidently wrong, ungrounded or unsafe answer, at ten times the expected cost.

The three pillars for AI: latency, quality, cost

flowchart LR
    A[AI request] --> L[Latency<br/>TTFT, total, per-stage]
    A --> Q[Quality<br/>groundedness, relevance,<br/>task success, safety]
    A --> C[Cost<br/>tokens, tool calls,<br/>retrieval, infra]
    L --> T[Trade-off decisions<br/>model, prompt, k, cache]
    Q --> T
    C --> T

These three are coupled. A cheaper model lowers cost but may reduce quality; a larger top_k may raise quality but increases latency and cost. Observability exists to make those trade-offs measurable and reversible.

Failure modes that only AI observability catches

Failure Looks like in APM What you need
Silent quality regression after a prompt/model/index change Nothing Online evals + release annotations
Retrieval drift (stale/poisoned index, embedding model change) Nothing Retrieval relevance, context precision/recall, index freshness
Cost explosion (agent loop, long context, retry storm) Slightly higher latency Token/cost per trace, per tenant, per feature
Provider-side model update ("silent" version drift) Nothing Pin model versions; track response fingerprint & eval baselines
Hallucination / ungrounded answers 200 OK Groundedness / citation-support score
Prompt injection, data leakage, jailbreak Nothing Guardrail verdicts, PII detections, red-team canaries
Agent loops, wrong tool selection Long latency Step counts, tool-call success, trajectory evals
Rate limiting / quota exhaustion 429s Per-model quota headroom, fallback rates

Outcomes you should be able to claim

  1. Detect a latency, quality or cost regression within minutes (alerts) or days (trend/drift).
  2. Explain any single bad answer end-to-end (trace → retrieved chunks → prompt → model → answer → evaluator score).
  3. Attribute cost to tenant, feature, model, prompt version and team (FinOps/showback).
  4. Prove to risk/compliance what the system did (audit, lineage) without over-collecting personal data.
  5. Trend all of the above over months, annotated with every change (model, prompt, index, config, code).

How AI observability differs from traditional APM

Dimension Traditional services AI applications
Behavior Deterministic; same input → same output Non-deterministic; temperature, retrieval and model drift
Correctness signal Status code, assertions Needs evaluation (heuristic, model-as-judge, human)
Latency shape Roughly normal; p99 meaningful Long-tailed, depends on output length; need TTFT and tokens/sec
Cost model Mostly infra (CPU/memory), flat-ish Per-token and per-call variable cost on every request
Payloads Small, structured, mostly safe to log Large free-text prompts/responses; contain PII and secrets
Dependencies Services, DBs Model providers, vector DBs, rerankers, tools, MCP servers, other agents
Failure Errors, timeouts Plausible-but-wrong, refusals, loops, unsafe output
Change surface Code deploys Code + prompt + model version + index + embedding + config + tools
Debugging unit Trace of service calls Trace + retrieved context + prompt + tool I/O + judge scores
Retention need Days–weeks of detail Weeks of detail, months–years of aggregates (trend, regression, audit)

What stays the same

Do not build a separate silo. AI telemetry should ride on your existing observability stack where possible: same trace context propagation (W3C traceparent), same SLO and on-call practice, same identity and access model. The AI-specific layer adds semantics (prompts, tokens, evals) not a parallel universe.

Rule of thumb

Reuse APM for infrastructure, golden signals and distributed tracing. Add an LLM-aware layer for content, evaluation, cost attribution and prompt/dataset management. Whether that layer is one product or two is the build-vs-buy question.

OpenTelemetry GenAI semantic conventions

OpenTelemetry defines gen_ai.* attributes, spans and metrics for model calls, agents and tool execution. Status: Development (not stable) as of mid-2026 — attribute and metric names may change between versions. Pin the semconv version you target and use OTEL_SEMCONV_STABILITY_OPT_IN as the conventions describe.

Commonly used attributes (verify against the version you target):

Attribute Meaning

gen_ai.provider.name (older: gen_ai.system) Provider, e.g. openai, anthropic, aws.bedrock
gen_ai.request.model / gen_ai.response.model Requested vs actually served model
gen_ai.request.temperature, .max_tokens, .top_p Request parameters

Key design decisions

  1. Gateway or no gateway? A gateway gives uniform metering and policy for all model traffic; it is the easiest place to get cost and rate-limit visibility. Instrumenting in-app gives richer semantic context (retrieval, prompt versions). Most enterprises do both: gateway for metering/policy, app SDK for semantics, joined by traceparent.
  2. Evaluation off the hot path. Never block the user request on an LLM judge. Emit trace → evaluate asynchronously → write scores back keyed by trace_id.
  3. Two stores, two jobs. Traces optimize for debugging a single request (short retention, high detail). A wide per-request fact table optimizes for trend analysis (long retention, columnar, cheap aggregates). Do not try to serve month-over-month analytics from a trace backend.
  4. Rollups for long ranges. Dashboards over 6–18 months must read pre-aggregated data (see Storage & retention).
  5. Release annotations. Every deploy, prompt version, model change, index rebuild writes an annotation/event so a trend shift can be tied to a cause.

Design patterns for AI observability

Instrumentation patterns

1. Gateway metering

Route all model calls through an AI gateway that stamps tenant, feature, model, tokens, cost on every call. Gives complete cost coverage even for un-instrumented apps. Trade-off: extra hop (~ms) and a shared failure domain — deploy redundantly.

2. OTel-first, vendor-second

Instrument with OpenTelemetry; export to a Collector; fan out to one or more backends. Benefit: swap vendors without touching app code.

3. Semantic wrapper (decorator) layer

Wrap retrieve(), rerank(), generate(), call_tool() in your own thin library that emits spans with the app.*/rag.* namespace. One library, used by every team, enforces consistent attributes and redaction.

4. Trace-linked evaluation (score write-back)

Evaluators consume sampled traces and write scores back to the same trace_id. Dashboards then slice quality by any trace attribute (tenant, prompt version, index version).

5. Shadow / canary evaluation

Send a copy of a sample of traffic to a candidate model/prompt/index; compare scores, latency and cost against production before promotion. Pair with feature flags and automatic rollback on SLO breach.

6. Golden-set regression gate

Curated Q&A set with expected facts/sources runs in CI and nightly in production-like config. A drop beyond threshold blocks release and pages the owner.

7. Feedback loop (data flywheel)

User thumbs/edits, escalations, and low-score traces are queued for review, triaged, then promoted into the golden set. Closes the loop between production and offline evaluation.

Data patterns

8. Wide event per request

Persist one denormalized row per request/turn (50–150 columns) with latency per stage, tokens, cost, config versions, eval scores and user outcome. Cheap to aggregate for any time range; the backbone of trend analysis. See Storage.

9. Tiered retention

Full detail short, aggregates long, raw content only where policy allows. See Storage.

10. Content by reference

Store prompt/response bodies in a governed, access-controlled store; keep only IDs, hashes, lengths and redacted snippets in the general telemetry path.

11. Change events as first-class data

Deploys, prompt versions, model switches, index rebuilds, embedding changes, feature-flag flips, provider incidents — all written as events so dashboards overlay them on every chart.

Reliability patterns

12. Telemetry must not break the app

Async batching, bounded queues, drop-on-overflow, timeouts; never block the request on export. Measure telemetry loss itself (dropped spans).

13. Budget guardrails

Per-tenant/feature token and cost budgets enforced at the gateway, with burn-rate alerts (e.g. 2% budget in 1 hour) and circuit breakers for runaway agents (max steps, max tokens, max wall-clock).

14. Provider fallback with attribution

Fallback chains (primary → secondary model) must record which model served the response; otherwise quality and cost shifts are invisible.

Anti-patterns

Anti-pattern Why it hurts
Logging full prompts everywhere "just in case" PII/secret exposure, huge storage bills, compliance risk
Judging 100% of traffic with a frontier model Evaluation cost rivals product cost; sample and tier judges
Only averages Long-tailed latency and cost hide in p95/p99 and top-1% tenants
No version tags Cannot attribute a regression to a prompt/model/index change
Treating thumbs-up as ground truth Sparse and biased; combine with automated and human evals
Separate silo per team Inconsistent attributes make enterprise rollups impossible
Alert on every score dip Alert fatigue; alert on SLO burn and statistically significant shifts

Why a wide fact table

One row per request/turn means any question — "p95 retrieval latency by index version for tenant X in March" — is a single GROUP BY. Metrics TSDBs cannot answer high-cardinality questions (tenant × prompt × model) cheaply; traces cannot do cheap aggregates over months.

See the schema in examples/sql/clickhouse_schema.sql and queries in Dashboards & queries.

Rollups and percentiles

  • Store histogram/quantile states (quantilesTDigest, quantileState, or Prometheus native/classic histograms) in rollups. Never average percentiles — merge their states.
  • Keep three granularities: 1-minute (alerting, ≤30 d), 1-hour (weeks–months), 1-day (quarters–years).
  • Roll up by dimension sets you actually need: {app, env}, {app, tenant}, {app, model}, {app, prompt_version}, {app, index_version}.
  • Cardinality guardrails: never put user_id, trace_id, or raw query text on metric labels. Tenant is acceptable only with a bounded tenant list (use top-N + "other").

Sampling strategy

Traffic Strategy
Errors, guardrail hits, slow (> p95), low eval score, thumbs-down Keep 100% (tail-based sampling)
High-value tenants / regulated flows Keep 100% of metadata; sample content
Healthy bulk traffic 1–10% for full traces; 100% for the wide fact row and metrics
Online evaluation Stratified sample (per tenant/feature/intent), e.g. 2–5% + all flagged traces

Always compute metrics from unsampled data (Collector spanmetrics/signaltometrics before the sampler, or app-side metrics) so rollups are not biased.

Sizing back-of-envelope

requests/day   × avg spans/request × ~1 KB/span   = hot-tier bytes/day
requests/day   × ~1–2 KB wide row (compressed 5–10x) = warm-tier bytes/day
content bytes  = requests × (prompt+context+answer chars) — dominant; gate with policy

Example: 5 M requests/day × 15 spans × 1 KB = 75 GB/day raw traces (before compression and sampling) — which is why full-trace retention is days, not months, while the wide row (≈10 GB/day raw, ≈1–2 GB compressed) comfortably covers 18 months.

Time-range UX requirements

  • Dashboards pick the rollup granularity from the selected range (≤6 h → 1-min; ≤14 d → 1-hr/5-min; >14 d → 1-hr/1-day).
  • Always show release/prompt/model/index annotations on the time axis.
  • Provide period-over-period (week-over-week, month-over-month) and baseline bands (rolling 28-day median ± MAD).
  • Retain eval scores at the same granularity as latency so quality and latency can be viewed together.

Security, privacy & governance

AI telemetry contains the most sensitive data your company produces at scale: employee and customer questions, internal documents (via retrieval), and model outputs. Treat the observability platform as a regulated data system.

Threats and controls

Risk Control
PII/PHI/PCI/secrets in prompts and responses Redact at the edge (SDK or Collector transform/redaction processors, or Presidio-style detectors) before export; deny-list for known secret formats
Over-collection of content Default to metadata only; content capture is opt-in per app, per tenant, per environment, time-boxed
Unauthorized access to traces RBAC/ABAC mapped to tenant and data classification; audit access logs; break-glass workflow
Cross-tenant leakage in shared dashboards Tenant-scoped views / row-level security; separate projects per business unit if needed
Vendor data residency & training use Region pinning, DPA, "no training on customer data", BYOK; prefer self-hosting or Collector-redacted SaaS for regulated data
Retention beyond policy / right-to-erasure TTLs per tier; deletion by subject_id pseudonym; content-by-reference makes erasure tractable
Prompt injection via retrieved docs, observed in traces Track injection detections; treat trace content as untrusted when rendering (escape HTML/markdown, never auto-execute)
Telemetry as exfiltration path Egress allow-lists for exporters; private endpoints

Data classification for AI telemetry

Class Examples Default handling
Operational metadata Latency, token counts, model, status, versions Broad access, long retention
Business context Tenant, feature, intent label, cost Role-based access, long retention

Governance and compliance mapping

  • Model & app inventory: every AI app registered with owner, risk tier, model(s), data sources — feeds dashboards and audits.
  • Regulatory alignment: EU AI Act (logging/traceability for high-risk systems, post-market monitoring), NIST AI RMF (Measure/Manage functions), ISO/IEC 42001 (AI management system), SOC 2 / HIPAA / GDPR for data handling. Observability evidence (eval results, incident records, change history) is the raw material for these.
  • Audit trail: immutable record of who changed which prompt/model/index/guardrail and when, linked to subsequent metric shifts.
  • Human oversight: review queues for flagged traces with documented outcomes.

Safety observability (what to detect and log)

  • Guardrail verdicts per category (toxicity, PII, jailbreak, prompt injection, off-topic, policy) with action taken (block/redact/warn).
  • Refusal rate and over-refusal (false positive) rate — both are quality signals.
  • Groundedness failures on regulated content (medical, legal, financial).
  • Red-team canary prompts run continuously against production config.
  • Tool-use authorization decisions for agents (what was allowed/denied and why).

Minimum viable control set

  1. Metadata-only by default; content capture behind a flag.
  2. Redaction in the Collector, tested with seeded PII fixtures in CI.
  3. Tenant-aware RBAC and audit logging on the observability UI.
  4. Retention TTLs enforced by storage policy, not by convention.
  5. Documented data-flow diagram reviewed by security/privacy.

Triggers to revisit the decision

  • Observability spend > 10–15 % of the AI platform spend.
  • Vendor acquired / relicensed / enters maintenance mode (this has happened repeatedly in the category).
  • Move to multi-cloud or sovereign-cloud requirement.

  • New regulation requiring on-prem evidence retention.

Anti-patterns in the decision

  1. Building a trace UI from scratch — OSS options are mature; build only the differentiating layer.
  2. Buying a platform but skipping instrumentation standards — creates lock-in at the SDK level.
  3. Evaluating tools on demos, not on your traces — run a 2-week bake-off on real (redacted) traffic with a scorecard.
  4. Ignoring exit cost — require a data-export path and OTel compatibility in the contract.

Bake-off plan (2 weeks)

  1. Pick 2–3 candidates covering different archetypes (e.g. SaaS, OSS self-host, cloud-native).
  2. Instrument one real RAG flow through the same Collector, fan out to all candidates.
  3. Run the same 200-question golden set + a replay of 1 day of redacted traffic.
  4. Score: setup effort, trace fidelity, eval workflow, dashboards for latency/quality/cost, query flexibility (can you answer "p95 retrieval latency by index version last quarter"?), export, access control, cost projection.
  5. Decide; document in an ADR.

Cloud-agnostic approach

Goal: keep instrumentation, data and dashboards portable across AWS, Azure, GCP, on-prem and multiple model providers.

Principles

  1. OpenTelemetry end to end — SDK → Collector → any backend.
  2. Own the Collector — redaction, sampling and routing logic lives in your config, not in a vendor.
  3. Own the wide fact table — long-range truth sits in a store you control (ClickHouse, Iceberg/Parquet lakehouse, or your warehouse).
  4. Gateway abstraction — LiteLLM/Portkey/Envoy AI Gateway/TensorZero abstract providers and meter usage uniformly.
  5. Kubernetes-friendly — everything deployable via Helm/Terraform on any cloud.

Levers to cut observability cost (any option)

  1. Sample healthy traces, keep 100 % of errors/slow/low-score (tail sampling).
  2. Compute metrics before sampling; sample only the trace bodies.
  3. Content by reference, truncated content, shorter hot retention.
  4. Tier judges: heuristic checks on 100 %, small-model judge on sampled, frontier judge on flagged/golden sets.
  5. Drop low-value spans (internal chunk-loop spans) — aggregate into attributes instead.
  6. Compress and downsample warm data into rollups.

Decision hint

If observability + eval cost projects above ~10 % of LLM inference spend, or the vendor price curve is superlinear in your growth, evaluate self-hosting the high-volume path (traces, facts) while keeping SaaS for the high-value collaboration features (prompt management, annotation, eval UI).

Market dynamics to plan around

  • Consolidation. Observability platforms are being acquired by data, APM and AI-infrastructure companies (e.g. Langfuse by ClickHouse, announced January 2026; Helicone reported to have joined Mintlify in March 2026 and moved to maintenance mode). Insist on OTel ingest/export and data-export rights.
  • OpenTelemetry convergence. Nearly every vendor now ingests OTLP and GenAI semconv, shifting differentiation from collection to evaluation, analysis and workflow.
  • APMs moving up-stack. Datadog, Dynatrace, New Relic, Grafana, Splunk, Elastic ship LLM/agent modules; LLM-native vendors respond with broader infra and security features.
  • Agent observability (multi-step trajectories, tool calls, MCP) is the current frontier; assess trace UX for long, branching runs.
  • Evaluation cost is a first-class budget line; look for tiered/cheap evaluators and sampling controls.
  • Licensing drift. "Open source" ranges from MIT/Apache to source-available (Elastic License 2.0, FSL). Read the license for your intended use.

Evaluation criteria for any tool

  1. OTLP ingest and data export; GenAI semconv support level.
  2. Trace fidelity for RAG (retriever/reranker spans, chunk-level scores) and agents (nested steps, tool I/O, loops).
  3. Evaluation: built-in metrics, custom judges, online scoring on production traces, dataset/experiment workflow, CI integration.
  4. Cost: token → $ mapping with custom price tables, per-tenant/feature attribution, budgets.
  5. Time-range support: retention, rollups, SQL/API access for months-long trends.
  6. Security: SSO/SCIM, RBAC, audit logs, PII redaction, regions, self-host/BYOC.
  7. Scale and pricing model (per span/event/seat/GB) at 3× volume.
  8. Alerting and integrations (PagerDuty, Slack, Jira, CI).

Burn-rate formula

burn_rate = (observed bad-event ratio) / (1 - SLO target)
page when burn_rate(1h) > 14.4 AND burn_rate(5m) > 14.4     # ~2 % of 30-day budget in 1h
page when burn_rate(6h) > 6   AND burn_rate(30m) > 6
ticket when burn_rate(3d) > 1

  • Alert on user-visible SLO impact first; route diagnostic signals to dashboards.
  • Require minimum sample size before quality alerts (e.g. ≥ 200 scored traces/window).
  • Group by app + change event to avoid duplicate pages.
  • Every alert links to: dashboard, example traces, last change events, runbook (runbooks).

Making judges trustworthy

  1. Calibrate judges against 100–300 human-labelled examples; report agreement (Cohen's κ / Spearman).
  2. Pin judge model + prompt version; record in eval_version. Changing the judge breaks trend continuity — re-score a baseline slice when you do.
  3. Mitigate bias: position, verbosity, self-preference (use a different model family from the generator where possible).
  4. Use rubrics with decomposed claims (extract claims → verify each against context) rather than a single 1–10 score.
  5. Track judge cost and latency as first-class metrics.
  6. Run judge drift checks: re-score a fixed anchor set weekly.

Most enterprises will live in the bottom-right quadrant within a year: AI apps in production and AI assistants triaging their incidents. That is why the boundary matters.

Why you must keep them separate in your thinking

  1. Different failure modes. An AI app fails by being plausibly wrong; an AI SRE agent fails by being confidently wrong about your infrastructure, possibly with the ability to change it.
  2. Different data rights. Observability for AI deals with user content and prompts; AI for observability reads logs, configs, tickets and secrets-adjacent data across the estate.
  3. Different evaluation. The first needs scorers and golden sets for answers; the second needs replayed incidents, accuracy of root-cause hypotheses and action safety.
  4. Different blast radius. A bad chatbot answer harms one user; a bad automated remediation can take down a region.
  5. Different buyers and budgets. Platform/AI teams vs SRE/operations; don't let one purchase silently define the other.

Where the two meet (and what to watch)

  • AI observing AI. Using an LLM judge to score another LLM's answers (online scoring) is AI-for-observability applied to observability-for-AI. Calibrate the judge, avoid same-model self-grading, version it.
  • AI SRE investigating AI-app incidents. It needs the AI-specific context: prompt/model/index versions, retrieval health, eval scores, change events. Without them it will blame infrastructure for what is a prompt regression. Give it the telemetry contract.
  • Observing the observers. Every AI SRE agent, copilot and judge is an AI application and needs the same tracing, cost, quality and safety visibility: see Meta-observability.
  • Shared plumbing. OpenTelemetry, a Collector tier, a long-range store, a runbook library: the same foundations serve both.

Design rules:

  1. Read-only first. Start with query/context tools only. Add actions one at a time, each with its own risk review.
  2. Evidence or it did not happen. Every claim in an investigation must cite a query/result/trace the human can open. Reject answers without citations.
  3. Constrain query generation. Validate generated PromQL/LogQL/SQL (syntax, cost, time range, row limits), run with timeouts and read-only credentials.
  4. Least-privilege identity. The agent gets scoped, short-lived credentials per tool; tenant and data-classification boundaries apply to it as to any user.
  5. Context quality beats model size. Topology, ownership, SLOs, change events and clean runbooks are what make investigations correct. Garbage metadata means confident nonsense.
  6. Human approval for state changes, with a diff/plan shown and a rollback path; start with reversible, low-blast-radius actions.
  7. Everything the agent does is logged and traced (meta-observability).

Cost, ROI and procurement

  • Pricing models vary: per agent-second or "agent unit", per investigation, credit-based, seat-based, or bundled. Model cost per incident and per month at your incident volume, including runaway or looping agent scenarios.
  • ROI is toil and MTTR, but count verification time: if engineers must recheck every claim, the saving shrinks. Track "accepted without edits" rate.
  • Beware bundling: an assistant that only works well with one vendor's data layer is a lock-in decision. Prefer tools that consume OpenTelemetry-native data and expose their tool interfaces (for example via MCP) so you can swap.
  • Check SLAs for the assistant itself: on-call must still work when it is down.

What "supports OpenTelemetry" means in practice:

  1. Ingestion: can you send OTLP directly? AWS and Google expose first-party OTLP endpoints; Azure offers OTLP via an agent/Collector/AKS path with its own onboarding resources (and the Azure Monitor exporter remains the long-standing route).
  2. Semantic conventions: the OTel GenAI conventions are still in Development, so each cloud's UI reads a specific version of the attributes. Pin your instrumentation version and test that your spans light up the cloud's AI views.
  3. Protocol constraints: AWS endpoints are HTTP only (no gRPC) with request/size/series limits; Google's Telemetry API has its own quotas; Azure needs its onboarding resources (Application Insights, data collection configuration).
  4. Identity: SigV4 (AWS), Microsoft Entra ID (Azure), Google ADC/IAM (GCP). Your Collector must be able to authenticate; this is the main integration chore.
  5. What is not portable: the AI-aware UIs (Omni, Foundry, Vertex) depend on attributes and resource naming conventions specific to each platform even when the transport is OTLP.

The portable pattern

Instrument once with OpenTelemetry → send to a Collector you control → fan out. Each cloud's native backend becomes one exporter. You keep redaction, sampling and routing in your config, and you can add or swap backends (including the OSS stack) without touching applications.

Enterprise implementation guide: cloud-native AI observability

How to roll out observability for enterprise AI apps (RAG, agents, chatbots) on AWS, Azure and GCP, using each cloud's native stack with OpenTelemetry as the portable layer. Written for platform, SRE, security and AI teams.

1. Principles

  1. OpenTelemetry at the edge, native backend behind it. Applications emit OTel only; a Collector tier you own handles redaction, sampling, enrichment and routing to the cloud-native backend(s).
  2. One telemetry contract for all clouds. Same span names, attributes and metric names everywhere (contract); the cloud-specific parts are exporters and identity.
  3. Metadata by default, content by exception. Capture IDs, counts, scores and versions; gate prompts/responses behind policy, redaction and short retention.
  4. Central visibility, local ownership. Workload accounts/subscriptions/projects send to a central observability plane; teams see their own slice.
  5. Measure all three pillars. Latency, quality (scores) and cost on every dashboard (RAG playbook, scoring).
  6. Telemetry must not break the app, and its own health is monitored.

11. Cost control

  • Know the unit prices. CloudWatch bills ingestion/storage/queries by signal; App Insights by GB and retention; Cloud Trace/Monitoring/Logging by usage. Model them with the TCO sketch.

Online and offline scoring: overview

Scoring turns the behavior of an AI application into numbers you can trend, compare and gate on. There are two complementary modes, and mature teams run both from the same scorers.

When Before a change ships (CI, nightly), and on demand Continuously, after the response is served
Question answered "Is this change safe and better?" "Is production healthy right now, and this quarter?"
Ground truth Available (reference answers, expected sources, labels) Usually absent: reference-free scorers, user signals
Inputs Controlled, comparable run to run The real, shifting distribution

Offline scoring

Offline scoring evaluates a system against a fixed dataset under controlled conditions. It is your regression test suite and your experiment bench.

1. Build the datasets

Dataset Purpose Size to start Source
Golden set Curated, high-quality items with expected outcomes; the release gate 200-1000 SMEs + sampled production queries, labeled
Regression set Every past failure, kept forever grows Promoted from incidents, thumbs-down, escalations
Adversarial / safety set Injection, jailbreak, PII, policy edge cases, unanswerable questions 100-300 Red team, OWASP LLM Top 10 patterns
Anchor set Frozen slice re-scored on every judge or model change to keep trends comparable 50-200 Subset of golden
Replay set Redacted production traffic for latency/cost realism 1 day of traffic Trace store
Holdout Never used for tuning prompts; detects overfitting 20 % of golden Split once, freeze

Rules of thumb:

  • Stratify by intent, difficulty, tenant tier, language and channel; report per slice, because averages hide regressions in important slices.
  • Include unanswerable and multi-hop items; test abstention as a first-class behavior.
  • Store provenance per item: source, labeler, date, guideline version. Version the dataset (golden@2026-10-14).
  • For stochastic systems, run each item several times (3-20) and score every run.
  • Keep personal data out of datasets; redact production-derived items.

2. Choose scorers

Prefer cheap, deterministic scorers wherever they are valid, and add judges only for what code cannot check (Designing scorers).

  • Task-level: required-fact recall, exact/fuzzy match, execution accuracy, schema validity.
  • Component-level (find where it broke): retrieval recall@k / MRR / nDCG, reranker lift, tool-selection accuracy, argument validity.
  • System-level: groundedness, answer relevance, safety, abstention accuracy, format.
  • Operational, scored alongside quality: latency (p50/p95, TTFT), tokens, cost per request. A "better" answer that is 3× the cost is a trade-off, not a win.

3. Compare fairly

flowchart LR
    D[Dataset v1] --> B[Baseline config<br/>pinned model, prompt, index]
    D --> C[Candidate config]
    B --> S[Score every run]
    C --> S
    S --> P[Paired deltas<br/>same items]
    P --> CI[Bootstrap CI]
    CI --> V{Verdict}
  • Pin everything that is not under test: model version, temperature/seed, prompt, index snapshot, tool stubs/recorded responses, judge model and rubric.
  • Paired comparison: compute the per-item difference candidate − baseline, then a bootstrap confidence interval on the mean difference. Paired tests are far more sensitive than comparing two means.
  • Decide with intervals, not point estimates. "+0.02 [-0.02, +0.06]" is not an improvement.
  • Report effect size and sample size next to every number; use more repeats rather than more adjectives.
  • Beware multiple comparisons: checking 30 metrics will show a "significant" change by chance. Pre-declare the primary metrics.

4. Gate

A gate has four kinds of conditions; fail the build if any is violated.

Condition Example
Absolute floor groundedness ≥ 0.85; citation present ≥ 0.90
No significant regression upper bound of CI of delta ≥ −0.02
Slice protection no intent drops more than 0.10
Hard safety 0 critical failures on the safety set; PII leak rate = 0
Operational p95 latency ≤ 1.10× baseline; cost ≤ 1.15× baseline

Online scoring

Online scoring evaluates live production traffic, with no reference answers, so you can see quality as users experience it and catch what the golden set never imagined.

Principles

  1. Never on the request path. Serve the user first; score asynchronously. A judge outage must not become a user outage.
  2. Cheap on everything, expensive on a sample. Deterministic checks and heuristics on 100 %; LLM judges on a stratified sample plus all flagged requests.
  3. Score, then write back with identity. Store (trace_id, metric, score, scorer_version, judge_model, ts) so any score can be sliced by any trace attribute: tenant, prompt version, index version, model.
  4. Read scores with their sample size. A dip on 12 samples is noise; show n and an interval on every chart.
  5. Version the scorer. A change in judge or rubric is a change in the measuring instrument; annotate it and re-score an anchor slice.

Architecture

flowchart LR
    APP[App] -->|trace + metrics| COL[Collector]
    COL --> TS[(Trace store)]
    TS -->|selected| Q[Bounded queue]
    SAM[Sampler] --> Q
    Q --> W[Scoring workers]
    W -->|fetch content via governed API| CS[(Content store, redacted)]
    W --> J[Judges / classifiers]
    J --> SC[(Score store<br/>+ metrics)]
    SC --> DASH[Dashboards + alerts]
    SC --> RQ[Review queue]

The runnable reference examples/scoring/online_scorer.py shows the sampler, bounded queue with load shedding, versioned write-back and interval reporting. The use cases emit the scores as OpenTelemetry histograms (rag_eval_score{metric="groundedness"}) with an eval_queue_age gauge, linked to the original trace.

What to score, and how often

Tier Scorers Coverage Purpose
T0: inline cheap checks schema valid, citation present, length, language, PII regex, banned terms, retrieval empty/low score 100 %, in-process (microseconds) Flag bad responses immediately; drive tail sampling
T1: async heuristics answer-to-context overlap, embedding similarity, toxicity classifier (small model) 100 % or high sample Cheap trend signal
T2: sampled LLM judge groundedness, relevance, task success, policy compliance 2-10 % stratified + all flagged The quality time series
T3: escalated judge / panel strong or multi-judge ensemble on contested items flagged + disagreements Reduce judge error where it matters
T4: human expert review queue small, targeted Ground truth and judge calibration

Cheap flags decide who gets the expensive judge: set eval.flagged=true on the span for empty retrieval, guardrail hits, thumbs-down, slow or costly requests, and use tail sampling to keep those traces.

Sampling

  • Stratify by app × tenant tier × intent × risk tier. Oversample high-risk and rare strata, otherwise rare intents never get a score.
  • Always score flagged requests (they are your triage queue) plus a small uniform random slice that is your unbiased estimator.
  • Do not pool the two. Flagged traces are over-represented in bad outcomes. Report the random slice as the health metric and the flagged slice as a work queue; the demo script prints them separately.
  • Re-weight (inverse probability) if you must report a single population-level number from stratified samples.
  • Shed load rather than block: a bounded queue, drop-oldest or drop-newest, and measure what you shed (eval_shed_total) so coverage stays honest.

Making noisy scores actionable

Technique How
Intervals and minimum n Alert only if n ≥ a floor (e.g. 200 per window) and the interval excludes the baseline
Baseline bands Compare to a rolling 28-day median ± MAD, per slice, same hour-of-week
Sequential tests / CUSUM Detect small persistent shifts earlier than fixed thresholds
Slice-aware alerts Alert on the worst important slice, not only the aggregate
Pair with leading indicators Retrieval top-1 score, empty-retrieval rate, index age: they move before judged quality does
Combine signals Quality alert = judge dip and retrieval dip or thumbs-down rise; fewer false pages

Online experiments

Pattern What it is Use for
Shadow Run candidate on a copy of traffic, score it, never show it Safe pre-launch comparison on real inputs; costs extra inference
Canary Send a small share to the candidate; auto-compare scores, latency, cost; auto-rollback Gradual rollout
A/B test Randomize users; compare scores and outcomes (resolution, task success) Product decisions
Interleaving / pairwise judge Judge A vs B answers to the same query Sensitive comparison with fewer samples

Always compare same slice, same scorer version, same period; randomize at the user or conversation level, not per request, for multi-turn apps.

User and business signals

Thumbs, edits, copy, regeneration, abandonment, escalation, ticket re-open, task completion. They are free and real but sparse, biased towards extremes, and delayed. Use them as a triage and calibration input (join to traces by trace_id), not as the only quality metric. Convert implicit signals into scored events (feedback.rating, outcome.resolved) and trend them next to judge scores; disagreement between them points at a bad judge or a bad rubric.

Privacy and governance

  • Workers fetch content through a governed, audited API with redaction; scores and metadata flow to the observability stack, raw content does not.
  • Respect data residency and tenant isolation in the scoring path (the judge sees customer content).
  • Record scorer versions and judge models in the score record; retain them as audit evidence.
  • Judges are LLM calls: apply the same budget, rate limits and failure handling as the product.

Designing scorers

A scorer maps an input/output (and sometimes context, trace or reference) to a number in [0, 1] or a label. Scorer quality bounds everything built on it.

Pick the cheapest valid scorer

flowchart TD
    Q{Can code decide it?} -- yes --> D[Deterministic scorer<br/>regex, schema, exact, SQL exec, unit test]
    Q -- no --> R{Do you have a reference?}
    R -- yes --> RB[Reference-based<br/>fuzzy match, fact recall, embedding sim]
    R -- no --> J{Is it a judgment call?}
    J -- yes --> LJ[Model-as-judge with rubric<br/>calibrated vs humans]
    J -- needs expertise --> H[Human review]

Order of preference: programmatic checks > reference-based > small-model judge > strong-model judge > human, escalating only where the cheaper tier is not valid. Programmatic checks are exact, free, reproducible and not subject to judge bias.

Model-as-judge: how to do it well

  1. Narrow, single-criterion rubrics. One judge call per criterion (groundedness, relevance, tone). Multi-criterion scores blur and correlate.
  2. Decompose. For groundedness: extract atomic claims from the answer, then verify each against the context; score = supported claims ÷ claims. More reliable than "rate 1-10".
  3. Categorical or binary outputs beat 1-10 scales. Use labels with definitions (supported / partially / unsupported) and map to numbers; add short reasoning before the verdict.
  4. Give anchors. Include 2-4 labeled examples per class in the prompt (few-shot), including borderline cases.
  5. Control randomness. Temperature 0, fixed seed where available, pinned model version; for noisy criteria use 3 votes and take the majority or mean.
  6. Pairwise for comparisons. "Which answer is better?" is more reliable than absolute scores; randomize order to cancel position bias.
  7. Use a different model family from the generator where possible, to reduce self-preference.
  8. Constrain output (JSON schema) and validate; treat malformed judge output as a scorer failure, not a low score.

Rubric template

Criterion: Groundedness
Definition: Every factual claim in the ANSWER is supported by the CONTEXT.
Steps: 1) list the claims, 2) for each claim, quote the supporting context or say "none",
       3) label each claim supported / unsupported.
Output JSON: {"claims":[{"text":"...","support":"supported|unsupported","evidence":"..."}],
              "label":"fully|partially|not_grounded"}
Mapping: fully=1.0, partially=0.5, not_grounded=0.0
Do not use outside knowledge. Ignore style and length.

Calibrate and validate the judge

A judge is a measurement instrument. Validate it before trusting it, and again after any change.

Step What to do
Label a calibration set 100-300 items, ≥ 2 human raters, written guidelines; measure inter-rater agreement first (the ceiling)
Measure judge-human agreement Cohen's κ / Krippendorff's α for labels, Spearman for scores; report per class and per slice
Check error structure False-positive vs false-negative rates; for safety scorers, recall on the positive class matters most
Probe for bias Position (swap order), verbosity (pad answers), self-preference (same-family generator), format, sycophancy to the answer's confidence
Test sensitivity Inject known defects (remove a fact, add a hallucination) and confirm the score drops
Track drift Re-score a fixed anchor set weekly; alert when judge output on it changes
Record cost and latency Judge tokens per score, p95 latency

Rule of thumb: if judge-human agreement is not close to human-human agreement, fix the rubric before scaling the judge.

Version everything

scorer: groundedness
version: 3
judge_model: judge-small-2026-08     # pinned
prompt_hash: 9f1c2e
rubric: groundedness@v3
calibration: {set: calib-2026-09, kappa: 0.78, n: 240}

Write scorer_version on every score. When it changes: annotate dashboards, re-score the anchor set under old and new versions, and publish the offset so trends stay interpretable.

Minimum viable scoring program (any app)

  1. Deterministic checks on 100 % of traffic and in CI.
  2. A 200-item golden set + a regression set, gated in CI with paired CIs.
  3. One reference-free judge criterion (groundedness or task success), sampled online, calibrated on 100 labeled items.
  4. User feedback captured with trace_id.
  5. Scores, versions and sample sizes on the same dashboard as latency and cost.

Operating a scoring program

Cost model

online judge cost/day  = requests/day x sample_rate x judge_calls_per_item x cost_per_judge_call
offline run cost       = dataset_items x repeats x (system_cost + scorer_cost) x runs/day

Example: 2 M requests/day, 4 % judged, one judge call at $0.0006 → ≈ $48/day. Judging 100 % with a frontier-model judge at $0.01 → $20,000/day: 400× more, for little extra statistical power.

Levers: tier scorers (T0-T4), stratified sampling, small-model judges calibrated against a strong judge, cached judge results for identical inputs, shorter judge inputs (claims instead of full documents), batch APIs for offline runs. Track judge cost per scored item and scoring cost as a share of inference spend as metrics (target under ~5-10 %).

Statistics you actually need

Need Method
Interval for a mean score Normal approx. (large n) or bootstrap
Interval for a pass-rate Wilson interval
Compare two configs on the same items Paired bootstrap on per-item differences
Compare two online arms Two-sample test / bootstrap on per-user (not per-request) means
Sample size for a detectable change n ≈ 2(2.8·σ/δ)² per arm for 95 % confidence and 80 % power (δ = smallest change you care about, σ = score std-dev)
Detect small persistent shifts CUSUM / EWMA on the score series
Many metrics at once Pre-declare primary metrics; correct (Holm/Benjamini-Hochberg) for the rest

Example: with σ = 0.11 and δ = 0.02, n ≈ 2 × (2.8 × 0.11 / 0.02)² ≈ 470 judged items per arm per window. That is why alerts need minimum-n guards and why rare slices need oversampling.

Reconciling online and offline

They disagree for known reasons; investigate rather than pick a winner.

Symptom Likely cause
Offline high, online low Golden set unrepresentative; production distribution shifted; data freshness; real user phrasing
Offline low, online high Reference-based scorer too strict; golden set harder than traffic
Same scorer, different mean Different judge version, prompt, or context truncation between the two paths
Online dip, offline stable Drift in inputs or index, provider-side change, a slice not in the dataset
Offline gate passes, canary fails Missing operational realism (load, tools, latency), caching differences

Practices: run the same scorer code and version in both modes; re-score a sample of production items offline under controlled config; measure the golden-set coverage of production intents; alert when coverage falls.

The improvement loop

flowchart LR
    ON[Online scores + feedback] --> FLAG[Flagged / low-score traces]
    FLAG --> TRI[Triage and label]
    TRI --> CAT[Classify cause<br/>retrieval, prompt, model, tool, data]
    CAT --> FIX[Fix]
    TRI --> REG[Add to regression set]
    REG --> GATE[Offline gate]
    FIX --> GATE --> CAN[Canary] --> ON

Weekly: review the lowest-scoring and most-disagreed traces; promote failures to the regression set; refresh 5-10 % of the golden set; review judge-human agreement on a sample; check alert noise.

Governance and audit

  • Keep score history, scorer versions, dataset versions and gate decisions as audit evidence (EU AI Act post-market monitoring, NIST AI RMF "Measure", ISO/IEC 42001).
  • Tier by risk: high-risk apps get higher sampling, human review queues and stricter gates (risk tiers).
  • Restrict who can edit gates and rubrics; changes are reviewed like code.

Anti-pattern Fix

  • Deterministic checks on 100 % online and offline
  • Golden, regression, adversarial, anchor and holdout sets versioned
  • CI gate with paired CIs, slice protection, hard safety and ops gates
  • Online sampler: stratified + flagged, bounded queue, shed counter

What to alert on

Empty retrieval rate, top-1 score median, groundedness rolling mean, TTFT p95, cost/request p95, index freshness, ingestion failures, ACL canary failures.

Golden practices

  • Version the index (index_version) and embedding model on every trace.
  • Log retrieved_doc_ids + scores always; chunk text only on sampled/flagged traces.
  • Build the golden set from real queries; include unanswerable and adversarial ones.
  • Re-run golden set on every index rebuild, chunking change, embedding change and model/prompt change.

Design choices (all from the handbook's pipeline guidance):

  • Metrics before sampling. spanmetrics sees 100 % of spans, so rates and percentiles are unbiased; only the trace bodies are sampled.
  • Tail sampling keeps what matters: every error, every slow (>8 s) trace, every trace flagged by cheap deterministic checks (eval.flagged), plus a baseline slice (25 % in the demo; use 1–10 % in production).
  • Redaction as a safety net, not the primary control. Apps already send IDs, lengths, scores and versions only.
  • Exemplars on: histogram buckets carry trace_id, which is what makes a latency panel clickable.
  • Self-observability: the Collector exposes its own metrics on :8888; platform.yml alerts on export failures, refused data and queue saturation.

Service support-chatbot: a customer-support assistant with multi-turn sessions across web, mobile and WhatsApp, intent routing, a guardrail that can refuse, escalation to humans, and streaming answers. Code: use-cases/chatbot/ · Theory: Monitoring chatbots.

Chatbots are judged per conversation, not per request. The metrics here are the ones a support leader asks about: containment, escalation, abandonment, and cost per conversation, next to the engineering ones.

Telemetry design

  • One trace per turn (chat.turn → chat <model>), correlated into a conversation by gen_ai.conversation.id. A session (the conversation) is a metric (chat.sessions) with a final outcome, so you never need to stitch traces to compute containment.
  • No message text is recorded: only message length, intent label, channel, turn index, context utilization and scores.
  • Streaming stalls and truncations are explicit events, because they show up in user abandonment before they show up in error rates.

Adapting the use cases to your app

Checklist

  1. Keep the names. Dashboards and alerts key on service_name and the metric names on each use-case page. Rename the service via setup("your-service"), then search/replace service_name="support-rag" in the rules and gen_dashboards.py.

RAG playbook: latency, quality & cost over any time range

Goal: full visibility into latency, quality and cost of the RAG app across any time range, catching issues early and tracking trends over months.

The recipe in seven steps

flowchart LR
    A[1 Instrument<br/>stage spans + versions] --> B[2 Meter<br/>tokens, cost, latency<br/>pre-sampling]
    B --> C[3 Store<br/>hot traces + wide facts + rollups]
    C --> D[4 Evaluate<br/>async, sampled, version-pinned]
    D --> E[5 Visualize<br/>range-aware dashboards + annotations]
    E --> F[6 Alert<br/>SLO burn, drift, cost]
    F --> G[7 Review<br/>weekly trend + monthly report]
    G --> A

1. Instrument every stage

Create spans for rag.request → rag.retrieve (embed, search, rerank) → chat <model> → guardrail. Attach app.*, rag.*, gen_ai.* attributes including prompt, model, index and embedding versions. Code: examples/rag-otel/instrument.py, guide: Instrumentation.

2. Meter cost and latency from 100 % of traffic

Compute metrics (counters, histograms) before trace sampling. Compute cost at request time from a versioned price table you own: cost = in_tokens × p_in + out_tokens × p_out (+ embed + rerank + retrieval infra).

3. Store for every time range

  • Hot (7–30 d): traces for debugging.
  • Warm (13–24 mo): wide per-request fact table (schema).
  • Rollups: hourly/daily with mergeable quantile states so a 12-month chart reads thousands, not billions, of rows.

4. Evaluate quality continuously

  • Deterministic checks on 100 %; small-model judge on a stratified sample; strong judge on flagged traces; humans on calibration sets (Evaluation).
  • Scores written back keyed by trace_id and stored with eval_version.

5. Visualize with time-range-aware dashboards

Panels that pick rollup granularity from the selected range, overlay change events and show sample sizes. Layout in Dashboards & queries.

6. Alert early

  • Minutes: error/TTFT burn-rate, cost spike, retrieval emptiness, agent/loop runaway.
  • Hours–days: quality regression vs 28-day baseline, drift, index staleness.
  • Every alert links to a trace sample, dashboard and runbook (Runbooks).

7. Review trends on a cadence

  • Weekly: SLO attainment, top regressions, cost anomalies, new failure clusters → backlog.
  • Monthly: month-over-month cost per resolved query, p95 latency, quality by intent, model/prompt/index change log vs metrics, budget forecast.
  • Quarterly: build-vs-buy re-check, evaluator calibration, retention/cost tuning.

Reading trends correctly

  1. Always compare same-slice, same-evaluator-version windows.
  2. Use rolling baselines (28-day median ± MAD) to tell drift from seasonality (weekday/weekend, month-end).
  3. Check traffic mix before blaming the system: Simpson's paradox is common when intent mix shifts.
  4. Show sample size / confidence intervals on every quality chart.
  5. Tie shifts to change events; if none exists, suspect provider-side model changes or data drift.

Instrumentation guide

Approaches

Approach Effort Fidelity Notes
Auto-instrumentation (OpenLLMetry, OpenInference, OpenLIT, vendor SDKs) Low Provider/framework calls Good start; misses business context
Manual spans with OTel API Medium High Needed for retrieval stages, versions, cost
Gateway metering Low Model calls only Complete coverage, no semantics
Framework callbacks (LangChain/LlamaIndex/…) Low Framework steps Often bridged to OTel

Recommended: auto-instrument model + vector DB clients, add a thin manual layer for stage spans and app.*/rag.* attributes, meter at the gateway.

Steps

  1. Pick conventions. gen_ai.* for model calls; your own app.*/rag.* for the rest (Telemetry model).
  2. Create a shared wrapper library (ai_telemetry) exposing context managers/decorators: retrieval_span, llm_span, tool_span, record_cost, record_feedback.
  3. Propagate context across services, queues and MCP/tool calls (traceparent; carry conversation_id as baggage or attribute).
  4. Stamp versions at startup from config/CI: release_id, prompt IDs/versions, model, embedding model, index version.
  5. Compute cost in the wrapper from a versioned price table (cached/reasoning tokens priced separately).
  6. Handle streaming: record TTFT at first chunk, close the span on stream end or client abort; record finish_reason.
  7. Capture feedback with the originating trace_id so thumbs/edits join to traces and scores.
  8. Gate content capture by flag + sampling + redaction.
  9. Test: unit-test the wrapper with an in-memory exporter; assert required attributes exist; seed PII fixtures to verify redaction.

Runbooks

Each alert should link to one of these. First move for any incident: check the change-event overlay (what changed in the last 24 h?).

Latency regression

  1. Confirm: TTFT vs total? p95 vs p50? Which tenants/features?
  2. Stage breakdown: which stage's share grew (embed / retrieve / rerank / LLM / tools)?
  3. Check provider status and regional latency; compare against another model/region if fallbacks exist.
  4. Check context_tokens and output length: longer prompts and answers drive latency and cost.
  5. Check vector DB saturation, index size/refresh, rerank service.
  6. Mitigate: reduce top-k/context, enable caching, route to faster model, scale replicas, shed load for low-tier tenants.
  7. Roll back the last change if correlated.

Quality regression

  1. Verify sample size and evaluator version (judge changes break trends).
  2. Slice: which intent/tenant/index/prompt version? Compare to the 28-day baseline.
  3. Inspect 10–20 lowest-score traces; classify: retrieval miss, ungrounded generation, prompt issue, format issue, data staleness.
  4. Retrieval metrics: top-1 score, empty rate, doc freshness.
  5. Check for provider-side model update (response_model, fingerprint) or embedding/index change.
  6. Mitigate: roll back prompt/index/model; pin versions; adjust retrieval; add guardrail.
  7. Add failing traces to the golden set.

Cost spike

  1. Break down by tenant, feature, model, prompt version, token direction.
  2. Look for: retry storms, agent loops (steps/task), context bloat (context_tokens), model change, cache miss surge, abuse/bot traffic, eval-cost surge.
  3. Apply guardrails: per-tenant rate limit/budget, max steps, max tokens, route to cheaper model.
  4. Fix root cause; add a regression alert.

Provider errors and rate limits

  1. Check error_type split (429, 5xx, timeout, content-filter).
  2. Verify quota/TPM headroom; request increase; spread across deployments/regions.
  3. Ensure fallbacks work and are attributed (fallback_used, response_model).
  4. Tune retries (exponential backoff + jitter, retry budget) to avoid amplifying the incident.

Retrieval degradation

  1. Empty-retrieval or low-score rate up? Which index/tenant?
  2. Check ingestion pipeline (failed docs, lag), index version, embedding model parity between query and index.
  3. Validate ACL filters (are legitimate docs excluded?).
  4. Re-run retrieval golden set; compare recall@k with last good index.
  5. Roll back index alias; fix ingestion; reindex.

Agent runaway or loops

  1. Confirm: steps-per-task p95, loop detections, terminations by reason (max_steps, budget_exceeded, timeout, loop), cost per task.
  2. Open a few traces of terminated tasks (span.loop.detected = true): which tool and arguments repeat? Is the tool returning an error or an empty result the agent keeps retrying?
  3. Check recent change events: prompt/tool-description edits, new tool, model switch, framework upgrade.
  4. Mitigate: tighten hard limits (max steps, per-task USD budget, wall clock), add a loop breaker (same tool + args ≥ 3 → replan or stop), disable the offending tool, route to a different model.
  5. Verify cost per successful task returns to baseline; add the failing trajectory to the regression suite.

Tool dependency failing

  1. Which tool (agent_tool_calls_total{status="error"} by tool)? Compare with the dependency's own health.
  2. Check retries/replans: failures amplify cost through plan revisions.
  3. Mitigate: circuit-break the tool, fall back to an alternate source, return a typed error the agent can reason about, cache stable results.

Conversation quality or containment drop

  1. Slice containment by intent and channel: one intent, or all?
  2. Compare refusals (over-refusal), fallbacks (unsupported intents), goal-completion judge score, thumbs-down.
  3. Check change events (prompt, model, retrieval/index, guardrail policy) and provider health.
  4. Read 10-20 escalated or abandoned conversations (redacted) and classify the cause.
  5. Mitigate: roll back prompt/model/guardrail policy; adjust thresholds; extend intent coverage; add failing cases to the golden set.

Context window pressure

  1. Context utilization p95, truncation events, tokens by turn index.
  2. Mitigate: summarize or window history, cap retrieved context, compress tool outputs, move long-term state to memory.
  3. Re-check cost per conversation and answer quality after the change.

Safety / guardrail incident

  1. Contain: tighten guardrail, disable affected feature/tool, block abusive tenant/user.
  2. Collect evidence (traces, policy decisions) under access control.
  3. Assess exposure (PII, cross-tenant) with security/privacy; follow breach procedure.
  4. Fix; add test cases to red-team suite; post-incident review.

Telemetry pipeline failure

  1. Check Collector metrics: refused/dropped spans, exporter failures, queue saturation.
  2. Fail open for the app (never block requests); enable local buffering.
  3. Backfill from logs/object store if available; annotate the gap on dashboards.

Post-incident

Blameless review: timeline with change events, detection gap (could we have caught it earlier with a leading indicator?), new alert/dashboard/golden-set items, owner and due date.

Term Meaning

OTLP OpenTelemetry Protocol for transmitting telemetry
Semconv Semantic conventions: standard names for attributes/metrics
GenAI semconv OpenTelemetry conventions for LLM calls, agents, tools (gen_ai.*)
OpenInference Arize-led conventions/instrumentors for LLM frameworks
Groundedness / Faithfulness Degree to which the answer is supported by provided context
Context precision / recall Share of retrieved context that is relevant / share of needed facts retrieved
LLM-as-judge Using a model to score outputs against a rubric
Golden set Curated evaluation dataset with expected outcomes
Online / offline eval Scoring production traffic / scoring a fixed dataset
Tail sampling Keep/drop whole traces after seeing them (errors, latency, flags)
Wide event / fact row One denormalized record per request with many columns
Rollup Pre-aggregated table at coarser time granularity
